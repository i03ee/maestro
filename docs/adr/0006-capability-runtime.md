# ADR 0006: طبقة تشغيل واحدة لكل قدرة، وبوابات بالترتيب

- **الحالة:** مقبول
- **التاريخ:** 2026-11-18

## السياق

إمكانات كثيرة يعني: أين تُنفَّذ؟ من يقرّر؟ ما الذي يمنعها؟ بلا مسار واحد، تتفرّق
القواعد: كل وكيل يقرّر وحده، فتختلف بوابات الأمان من مكان لآخر.

## القرار

1. `CapabilityRunner` واحد ينفّذ أي قدرة، ويمرّر المهمة عبر بوابات بترتيب ثابت:
   **عقد IR ← سجل القدرات ← الصلاحيات ← الميزانية ← التوجيه ← الدليل.**
2. أول بوابة ترفض تُوقف المسار فوراً، وتُعيد `ExecutionReport` فيه: المرحلة
   (`stage`) والسبب بالعربية. لا مسار «تجاوز» ولا متابعة بعد الرفض.
3. قدرة واحدة = وكيل واحد = بطاقة `CapabilitySpec` واحدة. السجل يمنع قدرتين
   في بطاقة.
4. الرفض **لا يترك أثراً في سجل الأدلة**؛ الأثر يُكتب للنجاح فقط. سجل الأدلة
   يثبت ما نُفِّذ، لا ما فشل —العمليات الفاشلة تُقرأ من تقرير التنفيذ.
5. التنفيذ الحرِج يُنفَّذ على السلسلة الأساسية الآن، ويُسجَّل في الدليل
   **المجموعة معلنة** (`ensemble`) و`min_agreement`؛ agreement الفعلي بين
   نماذج متعددة يُنفَّذ مع طبقة الوكلاء الحيّة (ADR 0001)، لا قبل ذلك.

## الآثار

- **إيجاب:** مسار تنفيذ واحد مفهوم؛ كل رفض له اسم مرحلة؛ الاختبار يستطيع
  إثبات «لم يُستدعَ النموذج» بعد الرفض.
- **سلب:** طبقة الوكلاء الحيّة (PydanticAI) لم تُفعَّل بعد — تحتاج مفتاح
  مزوّد وشبكة إلى PyPI. هذا موثّق صراحةً لا مخفي.
